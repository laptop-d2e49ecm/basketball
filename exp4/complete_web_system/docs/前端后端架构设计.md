# 实验 4 Web 系统 —— 前后端架构设计（v3）

> 项目：篮球 AI 赛事解说员（上传比赛视频 → 球员检测 → 中文逐事件解说）
> 本文档确定实验 4 的前后端技术架构，并预留实验 5（大模型解说）的接入边界。
> 部署模型：`A2_yolov8n/weights/best.pt`（3.2M 参数，val mAP50=0.418，原型演示水平，选型依据见实验 2 报告）。
>
> **v3 修订记录**：① REST 路径统一加 `/api/v1`，响应统一为 `{code,result,msg}`；② 前端组件库改为 Ant Design Vue；③ 视频检测框坐标统一为归一化中心点 `cx,cy,w,h`，并与交接代码的 `track_id` 命名一致；④ 视频 Worker 自动选择 CUDA 或 CPU；⑤ 保留 SQLite+Worker 本地模式，并预留 Celery+Redis 任务队列模式；⑥ 图像检测、文本分类、图文匹配作为独立课程页面；按组内分工由同学交付三页和对应 API，本侧视频主线只保留路由挂接点。

---

## 1. 总体架构

**B/S 架构，前后端分离；API 进程与推理 Worker 进程分离。** REST 统一使用 `/api/v1` 与 `{code,result,msg}` 信封；WebSocket 使用独立的进度通知消息格式。

MVP 交互形态：**上传视频 → 后端整段异步分析（WebSocket 推送阶段与进度）→ 完成后播放原视频，前端按时间戳叠加检测框与解说字幕**。不是直播式低延迟实时流。

```
┌──────────────────────── 前端 SPA (Vue 3) ─────────────────────────┐
│  视频解说主页面：上传 → 进度 → 回放叠框与解说                       │
│  独立课程页面：图像检测 / 文本分类 / 图文匹配                        │
└──────┬───────────────────────────────────────────┬───────────────┘
   REST（上传/任务/检测框/解说事件）     WebSocket（JSON：进度与事件通知）
┌──────▼───────────────────────────────────────────▼───────────────┐
│                   API 进程  FastAPI  uvicorn :8000                 │
│  REST /api/v1：tasks（上传/列表/进度）· detections · events · meta  │
│  ws/    /ws/task/{id}：阶段/进度/完成/失败通知                     │
│  db/    SQLite 任务表（状态持久化，重启不丢）                       │
└──────────────┬─────────────────────────────────────────────────────┘
               │ SQLite 任务表（认领 pending → running → ready/failed）
┌──────────────▼─────────────────────────────────────────────────────┐
│            Worker 进程（独立 Python 进程，启动即加载 best.pt）        │
│  解码抽帧(OpenCV) → YOLOv8n track 模式检测 → detections.jsonl       │
│  → 轨迹启发式事件 events.jsonl → CommentaryService（桩实现）        │
│  逐帧耗时与端到端耗时实测 → 写回任务表（作为采样决策依据）           │
└─────────────────────────────────────────────────────────────────────┘
```

## 2. 技术选型与理由

| 层 | 选型 | 理由 | 备选（弃用原因） |
|---|---|---|---|
| 后端框架 | **FastAPI (Python 3.12)** | 模型栈全是 Python（ultralytics/torch），零跨界成本；原生 async + WebSocket；Pydantic 强类型契约；自带 OpenAPI 文档便于前后端并行开发 | Flask（无原生 async/WS）；Django（对本项目过重）；Node.js（跨语言调 Python 模型多一层） |
| 任务持久化与执行 | **本地模式：SQLite（WAL）+ 独立 Worker；扩展模式：Celery+Redis** | 本地开发免额外服务、任务状态持久化；需要展示队列或多 Worker 时切换 Celery+Redis，复用同一视频处理函数 | 只放内存任务状态（重启即丢）；让 API 进程直接推理（长任务阻塞请求） |
| 前端框架 | **Vue 3 + Vite + TypeScript** | 组合式 API + `<script setup>` 上手快，适合 6 人课程团队分工；生态成熟 | React（可行，团队熟悉度优先）；Gradio/Streamlit（做不出视频叠加渲染，体现不了前端工程能力） |
| UI 组件库 | **Ant Design Vue** | 对齐实验任务书与同学交接契约，覆盖上传/进度/表格等课程演示组件 | Element Plus（功能可用，但与团队已定契约不一致） |
| 状态管理 | **Pinia** | Vue 3 官方推荐，管理任务状态与 WS 连接 | — |
| 通信 | **REST（数据）+ WebSocket（通知）** | REST 承载上传/任务/检测框/解说事件的请求-响应型读取（支持按时间范围）；WS 只推 JSON 进度/阶段/完成与解说事件通知 | SSE（单向）；MJPEG 直出渲染图（前端只剩"显示图片"，且带宽大） |
| 推理部署 | **Worker 进程内 ultralytics 加载 best.pt（设备 auto）** | CUDA 可用时选 GPU，否则用 CPU；设备由 `BASKETBALL_DEVICE` 覆盖；推理耗时为**待实测基线**（§3.2），实测后再决策采样间隔/imgsz | ONNX Runtime/OpenVINO（实验 3 优化项，按图像检测模块与实测结果使用） |
| 包管理/运行 | venv + pip（后端）、pnpm/npm（前端） | 与实验 1/2 环境习惯一致 | Docker（可选项，不作为课程演示依赖） |

### 3.2 视频分析流水线（关键设计）

MVP 主流程为**整段异步分析 → 完成后回放**；处理阶段 WebSocket 只推送阶段/进度/完成通知，检测与解说结果全部落盘供回放读取。

1. **解码抽帧**：OpenCV 按源帧率读帧（720p@25fps）。
2. **检测**：track 模式**逐帧推理起步**（`frame_step=1`），运行时自动选择 CUDA 或 CPU；逐帧推理耗时与端到端耗时全部实测，写回任务表（`avg_infer_ms / total_seconds`）。若 GPU 显存不足，应改用 CPU 或更小 `imgsz` 后重跑；当前自动选择处理“CUDA 是否可用”，不承诺从显存溢出中自动恢复。
3. **采样决策后置**：是否隔帧（`frame_step>1`）在拿到 M1 实测基线后再定。注意：**隔帧后跳过的帧不会有检测框**，ByteTrack 只跨采样帧维持 track_id，不会自动补框；若实测后采用隔帧且回放需要平滑，需另做轨迹插值——是否做同样由基线数据决定。`frame_step` 为配置项，默认 1。上传大小上限默认 5 GiB、可由环境变量调整；这是字节上限，不等于一小时视频都必然能通过，仍取决于编码码率和磁盘空间。
4. **事件组织**：轨迹启发式视觉线索（§3.4）。
5. **解说生成**：当前为桩实现（泛化文案，不依赖模型不存在的信息）。
6. **落盘**：`detections.jsonl`（`frame_idx,t_ms,image_w,image_h,boxes`）；每个 box 使用归一化中心点 `cx,cy,w,h`、`conf`、`track_id`，REST 支持按时间范围读取——回放与拖动进度条随机定位无需重算。

**性能基线（待实测，M1 验收项）**：在演示机（Ryzen 7 6800H，CPU）上用实际演示视频跑通 best.pt 全流程，记录每帧推理耗时、端到端处理耗时、处理帧率。后续所有性能决策（frame_step、轨迹插值、imgsz 降档、实验 3 ONNX 提速）以该基线为依据；本文档不预填估算值。

### 3.3 任务模型与持久化

- **SQLite 任务表**（`tasks.db`，WAL 模式），字段：`id, video_name, status, stage, progress, error, created_at, finished_at, frames_total, frames_done, avg_infer_ms, total_seconds`。**服务重启后任务状态与历史完好**。
- **独立 Worker 进程**：`python -m worker.main`，轮询认领 `status=pending` 的任务 → `running` → `ready/failed`，串行处理；模型启动即加载一次。API 进程只读写任务表，不做重计算。
- 单机单 Worker 场景无并发认领问题；将来扩展多 Worker 只需在认领处加事务。
- 状态机：`pending → running(解码/检测/事件/解说各阶段) → ready / failed`。

### 3.4 事件与解说的能力边界（重要，接口与文案共同遵守）

**现有模型只提供一件事：单类 `player` 的边界框；ByteTrack 的 track_id 仅是轨迹标识。**

| 信息 | 现状 | 来源 |
|---|---|---|
| 球员边界框 / 画面人数 / 位置 / 速度 | ✅ 检测+跟踪可得 | best.pt + ByteTrack |
| track_id | ⚠️ 仅轨迹标识，**不代表球员身份**（无球衣号码/姓名映射） | ByteTrack |
| 球队归属、球衣号码、比分 | ❌ 当前模型不提供 | 用户上传时填写比赛信息表单（可选）；或未来模型能力 |
| 语义动作（突破/投篮/助攻…） | ❌ 待 MultiSports 18 类动作识别 | 实验 5 |

- **事件按 `source` 字段分两级**：
  - `source: "heuristic"`（MVP 即有）：纯轨迹启发式视觉线索——画面人数变化、区域聚集（如篮下多人聚集）、整体运动方向突变；
  - `source: "action_model"`（实验 5 接入后）：动作识别模型输出的语义动作事件，Web 层不改，经同一事件通道流入。
- **解说文案与能力对齐**：MVP 桩解说只使用 heuristic 事件的泛化描述（如"画面中检测到 10 名球员，篮下区域出现聚集"），**不出现"7 号球员""蓝队""当前比分"等现有模型无法获得的信息**；队名/比分等上下文只允许来自用户填写的比赛信息表单。
- **质量口径与复核**：检测模型 val mAP50=0.418 属课程原型水平，漏检/误检可见。解说面板须标注"AI 生成，供参考复核"，每条解说可点击定位到对应画面时刻供人工核对。

### 4.2 检测框渲染（回放态）

`<video>` 播放原始视频；上层透明 `<canvas>` 在 `requestAnimationFrame` 中按 `video.currentTime` 从已拉取的 detections 数据取当前时刻的框，绘制边界框 + 置信度 + track_id。**框数据经 REST 拉取 JSON（归一化中心点 cx,cy,w,h），不走 WebSocket**——处理完成后一次拉取或按时间窗分段拉取均可。

处理中视图为 TaskProgress（阶段 + 进度 + 实测速率）；**"边处理边预览已落盘片段"列为可选扩展（轮询按时间范围读 detections），不进 MVP**。

## 5. 接口契约（视频模块已实现；独立课程模块按此接入）

所有 REST 成功响应使用 `{ "code": 0, "result": ..., "msg": "ok" }`；失败响应使用 HTTP 状态码作为 `code`，`result` 为 `null`，错误说明放在 `msg`。例如 HTTP 202 的任务创建响应仍使用 JSON `code: 0`。WebSocket 消息不是 REST 响应，不套用信封。

### REST

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/tasks` | multipart 上传视频 + 可选比赛信息表单字段（队名/比分），返回 `result: {task_id,status}` |
| GET | `/api/v1/tasks/{task_id}` | 任务状态：`task_id,status,stage,progress,frames_done,frames_total,avg_infer_ms,error` |
| GET | `/api/v1/tasks/{task_id}/detections?t_start&t_end` | 按时间范围的检测 JSON；坐标为归一化中心点，供回放叠框 |
| GET | `/api/v1/tasks/{task_id}/events` | 事件与解说列表（含 `source` 字段） |
| GET | `/api/v1/tasks` | 历史任务列表（读 SQLite） |
| GET | `/api/v1/meta/model` | 模型信息：名称/参数量/mAP50/类别/实测耗时（无估算值） |
| GET | `/api/v1/health` | API 健康状态 |
| POST | `/api/v1/detect`、`/api/v1/text/classify`、`/api/v1/match` | 同学负责的独立课程页面接口；视频解说主流程不调用这些接口，路径以联调契约为准 |

视频解说是本项目主流程。图像检测、文本分类、图文匹配按任务书保留为独立页面，各自调用自己的 API；视频解说不需要先调用文本分类或图文匹配。`/api/v1/match` 是团队可以采用的接口路径示例，任务书要求的是功能页面与交互，不限定必须使用这个具体路径。三类页面在同一导航中展示，但页面间互不阻塞。

### WebSocket `/ws/task/{id}`（处理阶段，纯 JSON 通知）

```jsonc
{ "type": "progress",   "stage": "detecting", "progress": 0.42, "frames_done": 315, "frames_total": 750 }
{ "type": "commentary", "t_ms": 16000, "text": "画面中多名球员向篮下区域聚集", "event": "cluster", "source": "heuristic" }
{ "type": "done",       "stats": { "frames_total": 750, "players_tracked": 10, "avg_infer_ms": null /* 实测值 */, "total_seconds": null } }
{ "type": "failed",     "error": "视频解码失败: ..." }
```

（检测框数据不经 WS；回放时走 REST 按时间范围读取。）

### 与实验 3/5 的对接边界（给组员的契约）

- **实验 3（模型优化）**：交付新 `best.pt`（或 ONNX）放入 `backend/weights/`，Worker 按文件加载，Web 层零改动；是否切换 ONNX 以 M1 实测基线的对比数据为依据。
- **实验 5（解说 Agent）**：实现 `CommentaryService` 接口——输入：`Event{t_ms, type, source, tracks[{tid, 轨迹摘要}]}` + 可选比赛信息（用户输入）；输出：中文解说文本（可流式）。**接口不假设当前模型不存在的信息**（球员身份/自动比分）；语义动作经 `source="action_model"` 事件通道进入；LLM 调用与 RAG（直播吧 4 万条语料）封装在模块内，不感知 Web 层。

## 6. 联调与部署

- **开发（三个进程）**：`uvicorn app.main:app --reload --port 8000`；`python -m worker.main`；`pnpm dev`（:5173，proxy `/api`、`/ws` 到 :8000）。需要演示队列模式时再启动 Redis 与 Celery Worker。前端 `types/` 依后端 OpenAPI schema 对齐，前后端并行开发。
- **课程演示（单机）**：`pnpm build` 产物由 FastAPI `StaticFiles` 托管；提供 `start.ps1` 一键顺序拉起 API + Worker 两个进程。
- **可选加分**：`docker-compose.yml`（API + Worker 共用镜像、不同入口），不作为演示依赖。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 服务重启丢任务状态 | SQLite 持久化（v2 已消除） |
